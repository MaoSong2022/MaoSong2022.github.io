## Async RL

Async RL, 即异步强化学习，是一个相对于 on-policy RL 的概念。

在 on-policy RL 中，我们一个训练是一个包含三步的循环: generator 通过 rollout 产生数据 -> trainer 更新 policy model -> generator 更新权重。在这个过程中，不考虑 [training inference mismatch](https://maosong.website/blog/train_inference_mistahch/) 的话，我们可以将训练近似看作是 on-policy, 即模型基于模型本身产生的数据进行训练。

On-policy training 的好处在于能够减少 bias, 但是其问题在于，trainer 更新时，我们的 generator 实际上处于闲置状态，这导致了资源的浪费。因此，Async RL 被提出来用于降低计算资源的空置率。

### Background

PipelineRL [@PipelineRL] 给出了一个 RL 训练效率优化的目标

> To effectively use a larger number of accelerators $N$ to make average reward $R(t)$ at time $t$ grow faster.

PipelineRL 将这个目标进行了拆解，即将 $R(t)$ 视作 $R(S)$ 和 $S(t)$ 的复合函数，其中 $S(t)$ 是时间 $t$ 需要处理的样本数量。
这样，效率优化的目标 (learning speed) 就可以拆解为 learning effectiveness 和 learning throughput 两部分：

$$
\frac{\Delta R}{\Delta t} = \frac{\Delta R}{\Delta S}\times \frac{\Delta S}{\Delta t}
$$

on policy 的好处是 learning effectiveness 很高 （因为几乎没有样本被 clip），但是代价是 throughput 会非常低，提高 $N$ 并不一定能够提高 throughput. 这是因为 short sequence 生成之后，必须等待 long sequence 生成完毕。

我们将 trainer 和 generator 之间的区别称之为 staleness, 即假设当前 generator 的参数为 $\theta_k$, trainer 的参数为 $\theta_{n}$ ($n\geq k$), 则

$$
\mathrm{staleness} = n - k\geq0
$$

当 $\mathrm{staleness}=0$ 时，代表 on-policy RL, 反之则是 async RL.

### Methods

### Conventional RL

Conventional RL [@PipelineRL] 的解决方法为使用 mini-batch 来完成更新, 即 "generator 一次 rollout, trainer 多次 update", 对应的算法如下所示

<Algorithm title="Conventional RL">

- **Input**: current policy $\pi$, number of optimier steps per RL step G, training batch size $B$

**while** TRUE:

1. $\mu\gets \pi$

2. generate $BG$ sequences from $\mu$

3. split sequences in $G$ mini-batches of size $B$

4. **for** batch in batches:

   update policy $\pi$.

</Algorithm>

使用这个算法的相关工作有 Qwen3 [@Qwen3] 和 ProRL [@ProRL].

当 $G=1$ 时，算法退化成 on-policy RL.

Conventional RL 的缺陷在于

1. 当 $G$ 增大之后，数据会变得越来越 off-policy, 最终降低整体的 learning effectiveness.
2. 提高 $N$ 并不能保证 learning throughput 提升，当 $N$ 足够大时，单个 accelerator 的 throughput 反而会下降。

因此，Conventional RL 的上限同时由 staleness 和 throughput 决定。

### PipelineRL

PipelineRL [@PipelineRL] 与 Conventional RL 的策略有两点区别：

1. trainer 和 generator 以 async 的方式并行运行
2. trainer 收集到 $k$ rollouts 则立马进行参数更新，并将参数同步到 generator.

在 Conventional RL 策略中，staleness 沿 batch 纬度增加，越往后的 batch, staleness 越大，同一个 mini-batch sample 的 staleness 相等。而在 PipelineRL 中，staleness 沿 action/token 维度增加，同一个 sample 里，越往后的 action/token, 其 staleness 越大。算法伪代码如下所示

<Algorithm title="PipelineRL">

- **Input**: current policy weights $\pi$, generation batch size $H$, training sequence queue $Q_{\text{train}}$, optimizer state $\text{opt\_state}$, training batch size $B$

**Generator Process**:

1. $S_{\text{prog}} \gets []$

2. **while** TRUE:
   1. $S_{\text{fin}}, S_{\text{prog}} \gets \text{pop finished sequences from } S_{\text{prog}}$

   2. $Q_{\text{train}}.\text{put}(S_{\text{fin}})$

   3. **if** $\text{len}(S_{\text{prog}}) < H$:

      add $H - \text{len}(S_{\text{prog}})$ prompts to $S_{\text{prog}}$

   4. **if** Trainer requests weight update:

      $\mu \gets \text{receive\_weight\_update}()$

   5. $S_{\text{prog}} \gets \text{generate next tokens with } \mu$

**Trainer Process** ($\text{TRAINER}(\pi, \text{opt\_state})$):

1. $\text{batch} \gets []$

2. **while** TRUE:
   1. $\text{request\_actor\_weight\_update}(\pi)$

   2. $\text{batch} \gets \text{get } B \text{ sequences from } Q_{\text{train}}$

   3. $\pi, \text{opt\_state} \gets \text{optimizer\_step}(\pi, \text{opt\_state}, \text{batch})$

</Algorithm>

## Analysis

两种范式的对比如下表所示

| Mode            | learning effectiveness                     | Learning throughput                                |
| --------------- | ------------------------------------------ | -------------------------------------------------- |
| on-policy RL    | highest                                    | lowest                                             |
| Conventional RL | depends on $G$, lower is better            | depends on $G$, within the optimal range is better |
| PipelineRL      | depens on sequence length, lower is better | None                                               |

我们来定量分析一下两种范式的 throughput 和 lag.

我们先介绍几个符号：

1. $N$ 总 GPU 数量，我们假设使用其中 $I$ 张用于 generation, $H-I$ 张用于 training.
2. $H$ 是每张 GPU 同时处理的 sequence 数量，$B$ 是训练使用的 sequence 数量
3. $L$ 为 max sequence length, $\bar{L}$ 为平均 sequence length
4. $\tau$ 为每个 token 的训练耗时

Conventional RL 在生成过程中， 处理的 sequence 数量会逐渐减少，我们将第 $\ell$ 步仍在生成的序列记为 $h(\ell)$. 若我们有 $N$ 张 GPU, 则每张 GPU 平均处理 $h(\ell)/N$ 条仍然生成的序列，利用率为 $U(h(\ell)/N)$. 总的生成时间为

$$
t_{gen}^{Conv} = \sum_{\ell=1}^{L} \frac{h(\ell)/N}{U(h(\ell)/N)}
$$

训练阶段一共处理 $K$ tokens, 每个 token 的耗时为 $\tau/N$, 故总的训练时间为

$$
t_{train}^{Conv}=\frac{K\tau}{N}
$$

Conventional RL 的训练与生成是串行的，总时间为生成时间与训练时间之和，throughput 为

$$
r_{conv} = \frac{K}{t_{gen}^{Conv}+t_{train}^{Conv}}=\frac{1}{\frac{1}{r_{gen}^{conv}}+\frac{1}{r_{train}^{conv}}}
$$

这里 $r_{gen}^{conv}$ 和 $r_{train}^{conv}$ 分别为生成和训练阶段的 throughput.

因此，对于 Conventional RL 来说，生成或者训练任一阶段的 low throughput 都会降低整体的 throughput.

对 PipelineRL 来说，训练与生成并行工作，生成使用 $I$ 张 GPU, 每张以 batch size $H$ 运行，throughput 为

$$
r_{gen}^{pipeline}=U(H)I
$$

训练使用 $N-I$ 张 GPU, throughput 为

$$
r_{train}^{pipeline}=\frac{N-I}{\tau}
$$

总的 throughput 由训练和生成更慢的一个阶段决定

$$
r_{pipeline} =\min(r_{gen}^{pipeline}, r_{train}^{pipeline})
$$

因此，对于 PipelineRL 来说，整体的 throughput 取决于生成和训练两个阶段中较低的那一个，并且这两者会动态变化（因为总的资源固定）。

关于 staleness, Conventional RL 的 staleness 与 $G$ 和当前 mini-batch 有关，最小为 $0$ (第一个 mini-batch), 最大为 $G-1$ (最后一个 mini-batch).

在 PipelineRL 中，最长序列生成的 $L$ 个 decoding step 里，生成使用 $I$ 张 GPU, 每张 GPU 维护 $H$ 个序列，总共产生 $HIL$ tokens, 用 $\bar{L}$ 来换算，相当于

$$
\frac{HIL}{\bar{L}}
$$

条 sequence, 每 $B$ sequences 训练一次，相当于

$$
g_{\max}= \lceil \frac{HIL}{\bar{LB}} \rceil
$$

次优化更新，这就是 PipelineRL 的 staleness.
